<!-- Backend contract from Phase 1 (01-03) -->

POST /api/images/batch (multipart/form-data)
  Field 'files': image File — REPEATED up to 20 times under the same key (multer().array('files', 20))
  Fields 'quality' / 'format' / 'width' / 'height': shared options, same as /process
  Response 200: Content-Type: application/zip, body = streaming ZIP containing optimized-1.<ext>..optimized-N.<ext>
  Response 400: { error: 'MISSING_FILE', ... } | { error: 'INVALID_FILE_TYPE', ... }  (any HEIC in the batch → reject)
  Response 413: { error: 'FILE_TOO_LARGE', ... }  (any single file > 20MB)
  Multer rejects > 20 files at the body parser layer with 400 LIMIT_FILE_COUNT.

<!-- BATCH-03 implementation note (per RESEARCH.md Pitfall 7 / Open Question 1) -->

The batch endpoint is synchronous from the frontend's perspective — there is no per-file progress signal during server-side processing. BATCH-03 is implemented as:
  Phase A (upload): show upload percentage via onUploadProgress (0–100%)
  Phase B (processing): after upload hits 100% and before the ZIP arrives, show "Procesando N imágenes…"
  Phase C (complete): show "Descargar ZIP" button
This is documented behavior — do NOT attempt to implement a per-file counter that would require SSE in the backend.
